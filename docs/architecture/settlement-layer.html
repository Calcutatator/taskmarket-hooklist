How a relayed write settles

A relayed write is two on-chain transactions that cannot be made atomic: a payment we observe, and a contract call we dispatch. Everything below exists to decide what happened between them — from evidence, never from a timeout.

The happy path

Two rounds. The key is claimed on the round that carries payment, immediately before settlement.

  • before money moves — nothing durable is written
  • irreversible — written before it can be lost
  • ordinary progress

Why the claim sits there

Claimed before the challenge, the exchange's own second round finds a live reservation under its own key, cannot tell itself from a competitor, and is refused — every paid write broken for the length of the TTL. Claimed after settlement, two concurrent requests both settle. It goes on the round that carries payment, immediately before settling: that is the only round money can move on.

The one that was hardest

A send that never answered. The chain can only be asked about a transaction by hash — and there isn't one.

Most dangerous line

The receipt key must stay byte-identical to the Solidity. A Foundry test and a TypeScript test now pin the same vector from opposite sides.

The rules that never bend

Absence is not evidence

A missing receipt, an unanswered RPC, a nonce that looks free — none of these may settle anything. Every branch that cannot prove an outcome leaves the row exactly where it was. Reading "no answer" as "never happened" is what once refunded people whose work had landed, paying them back and giving them the result out of the server wallet.

Only four things may trigger a refund

A reverted receipt. A replacement mined at the same nonce, proving the original never can. An exhausted retry budget past the deadline the payer signed. A receipt key the chain says was never consumed, past that same deadline. Nothing else — and never a timer alone.

The deadline is the payer's, not ours

Refund timing is bounded by the validBefore in the authorization the user actually signed, which the forwarder enforces on chain. It is not a constant anyone tuned, so it cannot drift away from what was agreed.
